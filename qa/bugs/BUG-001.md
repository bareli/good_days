## Summary

WCAG 2.1 A, 2.4.3 Focus Order (and 2.1.1 Keyboard in practice): in the card, pressing Enter or Space on an
item's disclosure button, and the card's own one-minute re-render, both throw keyboard focus to `<body>`. The
keyboard user loses their place after every activation and every minute. The card's CHANGELOG (v0.1.0)
advertises "keyboard focus kept across refreshes"; the software does the opposite, so this also contradicts the
product's own statement. Applies to every user who navigates the card by keyboard or switch device, and to
screen-reader users (focus on `<body>`, the new `aria-expanded` state is never announced).

## Steps to reproduce

1. Dashboard with `type: custom:good-days-card` (`days: 60`, `limit: 8`), user `qa_admin`, language he, Chromium 153 (Playwright, headless).
2. Put focus on the first item button (`button.item`), press Tab once: the ring is on the second item (screenshot BEFORE).
3. Press Enter (Space behaves the same). The details open, `aria-expanded` becomes true on a NEW button, and `document.activeElement` is `BODY`; the focus ring is gone. Recorded events: `keydown:Enter, click, focusout:item-...`, no `focusin` afterwards.
4. Repeat without pressing anything: wait for the 60 s tick (`TICK_MS`). Same result: focus on item 2 before, `BODY` after (screenshot AFTER). The next Tab lands on the first item of the card, not the one after the item you were on.

## Expected

Focus stays on the control the user activated, through re-renders (WCAG 2.4.3; the code intends this: `_render()`
restores focus by `data-focus-key`; CHANGELOG v0.1.0).

## Actual

`_render()` rebuilds the whole shadow tree and then calls `again.focus()` synchronously. The freshly created
`ha-card` is a Lit element whose shadow root has not rendered yet (its `<slot>` is created on the next microtask),
so its light-DOM children have no layout box and `focus()` silently does nothing. Measured: with `HTMLElement.prototype.focus`
wrapped, `focus() on BUTTON key=item-... connected=true` is called and `shadowRoot.activeElement` is still `null` right after.
Item buttons inside the old tree are already gone, so focus falls back to `body`.

## Evidence

Playwright 1.63 / Chromium 153, scripts `gd-E.mjs`, `gd-E3.mjs` (scratch). Focus probe output:

```
focused "item-family-f32271ba...-2026-10-02"
AFTER TICK {"path":"body","tag":"body", ...}
```
No screen reader was run (none available on this machine); the focus loss is measured from the DOM, the missing
announcement is inferred.

## Likely root cause

Likely: focus restoration runs before the new `ha-card` has rendered its slot. Proof is the wrapped-`focus()` trace above.

## Relevant files

`custom_components/good_days/www/card.js` `_render()` (lines ~426-436), `_renderInner()` (`ha-card` created at ~443).

## Recommended remediation

Restore focus after the card has rendered: `await card.updateComplete` when present (or `requestAnimationFrame`), then `.focus()`.
Better: avoid rebuilding the tree when nothing changed (the tick only needs to update countdown text). Keep the
`data-focus-key` restore for the real data refresh.

## Regression test

A11Y-001. A unit test cannot hold it: focus order is a browser measurement. A frontend harness test with a
stub `ha-card` that defers rendering would pin the markup only.
