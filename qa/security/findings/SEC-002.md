## Summary

Handler behaviour reproduced; the non-admin route to it is reasoned from Home Assistant's source, not
reproduced, because `mobile_app` is not loaded on the dev instance.

`reminders.async_register_actions` listens to `mobile_app_notification_action` and trusts the
`action` string `GOODDAYS:<ack|snooze>:<entry_id>:<date_id>:<day>` completely: `date_id` and `day`
are stored as given, with no check that the date exists or that `day` is an ISO date.
`acked` keys are pruned only when `day < cutoff` as a string compare, so a `day` such as
`9999-12-31` is never pruned; `snoozes` accepts any strings.

## Steps to reproduce

1. As admin (the only identity that can fire events over WS; `qa_user` gets `unauthorized` for
   `fire_event`, checked), fire the same event the Companion app would send:
   ```
   {"type":"fire_event","event_type":"mobile_app_notification_action","event_data":{"action":"GOODDAYS:ack:<entry_id>:not-a-date-id-SECQA:9999-12-31"}}
   {"type":"fire_event","event_type":"mobile_app_notification_action","event_data":{"action":"GOODDAYS:snooze:<entry_id>:not-a-date-id-SECQA:not-a-day"}}
   ```
2. Read `reminders` in `.storage/good_days.<entry_id>`.

## Expected

The handler ignores an action for a date that does not exist or a `day` that is not a valid ISO date
(my inference; PROJECT.md *Fix constraints*: "Server-side validation for every input path").

## Actual

```
"acked": {"not-a-date-id-SECQA:9999-12-31": "9999-12-31"},
"snoozes": [{"date_id": "not-a-date-id-SECQA", "day": "not-a-day", "due": "2026-10-01T23:15:22+03:00"}]
```
Both persisted. The `acked` entry will never be pruned (`"9999-12-31" < cutoff` is false).

## Reachability for a non-admin (reasoned, not reproduced)

HA's `mobile_app` webhook command `fire_event` (`homeassistant/components/mobile_app/webhook.py`,
`webhook_fire_event`) fires any `event_type` with any `event_data` for any registered device, and any
authenticated user, admin or not, can register a device (`POST /api/mobile_app/registrations`, or
simply by logging into the Companion app). So every household member with the app can send these
events. The entry id is visible to non-admins (`good_days/timers/get`, `dates/list`).

## Impact in this product's threat model

Small. A family member can already delete any family date (open by design), so suppressing a
reminder with a forged "Got it" gains nothing. What is new is unbounded, never-pruned growth of the
`.storage` file with attacker-chosen strings, bypassing the 500-date cap: each forged ack adds a
permanent key. Nothing executes and no data crosses a boundary.

## Relevant files

- `custom_components/good_days/reminders.py` (`async_register_actions._on_action`, `async_ack`, `async_snooze`, `_prune`)

## Recommended remediation

In `_on_action`: ignore unless `runtime.store.get(date_id)` exists and `dt.date.fromisoformat(day)`
parses and is within the reminder window (e.g. within `REMINDER_LOOKBACK_DAYS` / `MAX_REMINDER_DAYS`
of today). Optionally cap `snoozes` length.

## Regression test

REM-004. A pytest firing `mobile_app_notification_action` with an unknown `date_id` and with
`day="9999-12-31"` asserts `store.reminders["acked"]` and `["snoozes"]` are unchanged; the valid
ack / snooze tests must still pass.

snooze clears itself after it fires).
