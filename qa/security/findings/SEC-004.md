## Summary

SECURITY RISK, reasoned from the code and Home Assistant's source; not reproduced end to end
because the dev instance has no script, automation, lock, cover or valve entities.

`timers.TARGET_DOMAINS` accepts `script`, `automation`, `lock`, `cover` and `valve`, and
`TimerManager.async_execute` runs every rule as `homeassistant.turn_on` / `turn_off`:

1. **script / automation**: `homeassistant.turn_on script.x` runs the script, i.e. any action at
   all; `turn_off automation.x` disables an automation. SPEC §12.4 (Victor, 2026-09-30) says
   "actions stay on/off + scenes (no arbitrary services)". Only admins can save rules, and an admin
   can already run any script, so no privilege is gained. But the stated constraint does not hold, and
   the call runs with no user context, so it shows up in the logbook as a system action.
2. **lock / cover / valve**: these domains have no `turn_on` / `turn_off` service.
   `homeassistant.async_handle_turn_service` skips them (`if not hass.services.has_service(domain,
   service.service): unsupported_entities...` then only logs a warning), so the call returns
   without error and the timer records `done`. For a lock this is safe (nothing happens), but the
   editor offers something that can never work, and the history says it did.

## Steps to reproduce

1. As admin: `{"type":"good_days/timers/save","name":"SEC lock","targets":["lock.front_door"],"action":"on","anchor":"clock","time":"10:00","applies_to":["shabbat"]}`
   -> `{"errors":{"targets":"unknown_targets"}}` on dev only because no lock exists. The domain
   passes the `TARGET_DOMAINS` check; with an existing lock the rule saves.
2. Read `homeassistant/components/homeassistant/__init__.py` `async_handle_turn_service` (lines about
   120-175 in HA 2026.9): domains without the service are collected into `unsupported_entities` and
   only logged.
3. `timer_manager._async_run` records `STATUS_DONE` whenever `async_execute` does not raise.

## Expected

Source: SPEC §12.2 / §12.4 (on/off for switch, light, input_boolean, fan, climate, water_heater,
plus scenes; no arbitrary services). My inference: a rule for a device the action cannot operate is
refused at save time, not recorded as done.

## Actual

Reasoned above. The dev instance rejects the lock only as `unknown_targets` because none exists.

## Impact in this product's threat model

Admin-only input, so there is no path for a non-admin (checked: every `timers/*` write returns
`unauthorized` for `qa_user`). The risks are an owner-stated constraint that does not hold, and a
false `done` for a device that cannot be operated. For a lock, the false `done` means the admin
believes the door was handled for Shabbat when it was not.

## Relevant files

- `custom_components/good_days/timers.py` (`TARGET_DOMAINS`)
- `custom_components/good_days/timer_manager.py` (`async_execute`, `_async_run`)

## Recommended remediation

Owner ruling on scripts / automations (hence `model:opus`). Either drop `script`, `automation`,
`lock`, `cover` and `valve` from `TARGET_DOMAINS`, or map each domain to its real service
(`lock.lock/unlock`, `cover.open/close_cover`, `valve.open/close_valve`) and document it. Either
way, record `failed` rather than `done` when a target's domain has no matching service.

## Regression test

TMR-001. A pytest that saves a rule with a `lock.*` target, then asserts either a validation error or
that `lock.lock` was called. A second test asserts that `script.*` / `automation.*` are refused, or are
allowed, as ruled.
